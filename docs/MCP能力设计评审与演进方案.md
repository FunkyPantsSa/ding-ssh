# MCP 能力设计评审与演进方案

日期：2026-11-21。范围：当前工作区源码中的 MCP、HTTP 控制面、宿主执行器、前端调试桥及关联 SSH/SFTP 能力。本文件保留初始设计评审。用户已批准实施，落实状态与检验结果见同目录《MCP改造实施与验证记录》。原始证据行号对应评审时源码。

## 1. 总体判断

现有实现已经具备较完整的应用控制面，主要短板是权限语义、执行可靠性和业务闭环。建议保留已有工具与 HTTP/stdio 接入，围绕统一策略执行器逐步改造，不整体重写。

当前工具条目按源码计数为 **98 个**：内置 26、UI 25、应用控制 34、SFTP/终端自动化 12、sudo 1。README 仍写 89，部分文件头注释也未跟随新增能力更新。分组、服务器测试、主机信任列表、标签激活和分屏已经实现，不应再次作为新增功能立项。

优先级定义：P0 为权限/敏感数据边界，P1 为正确性与核心闭环，P2 为体验和扩展。下文的缺陷判断来自源码调用路径；涉及真实远端、操作系统权限或 GUI 行为的结论，仍需专门集成验证。

## 2. 已覆盖的能力与应保留的设计

| 领域 | 已覆盖 | 评价 |
| --- | --- | --- |
| 接入 | Streamable HTTP 请求响应、GET SSE 推送、stdio 代理、发现文件、运行时 token | 接入基础齐全，可继续复用 |
| 应用与工作区 | 状态、健康、标签、激活、面板、分屏、内置命令 | 已超出普通 SSH MCP，应保留语义化入口 |
| 服务器与组织 | CRUD、复制、移动分组、导入导出、分组管理、连接测试 | 覆盖较完整，下一步应改善过滤、分页和批量预检 |
| 凭据 | 元信息、创建、修改、删除、绑定，部分接口可显式读敏感字段 | 需要区分“使用凭据”和“导出凭据” |
| SSH 交互 | 缓冲读取、输入、run、expect、断开、重连、sudo | 交互基础较强，缺稳定的独立执行与任务生命周期 |
| SFTP | 列目录、分页、属性、分片读、写、追加、建目录、移动、删除、目录同步、传输查询/取消 | 缺直接上传下载闭环、条件写入和文件编辑原语 |
| 隧道 | 列表、配置与启动停止 | 缺可读的连通诊断和持续健康状态 |
| UI | DOM/样式/令牌/组件树/控制台/store、截图、差异、断言、合成事件、样式实验 | 适合开发调试，应与运维权限分开 |
| 权限与审计 | Gate、参数绑定的一次性确认 token、调用记录、设置撤销、输出大小限制 | 基础值得保留，需要修正它们承诺的边界 |

值得保留：HTTP 与 MCP 共用业务逻辑、写能力默认多数关闭、白名单为空禁止 SFTP 写入、调用被拒也记录审计、工具目录与权限登记有一致性测试、结构化输出逐步接入、设置可撤销、会话自动化有互斥保护。

## 3. 当前设计中应先调整的部分

### 3.1 P0：两段式 token 不是独立的用户审批

`confirm.prepare` 立即把可提交 token 交给同一调用方；`confirm.commit` 校验并执行。提示“请先展示给用户”属于客户端约定，服务端没有独立记录用户的批准行为。

当前机制能防参数替换、过期提交和重复使用，不能证明用户同意。也不能单靠它阻止 AI 自主扩权。

需要精确区分现有路径：`capability.enable` 的通用 commit 要求 **lifecycle**，并非任何只读客户端都能直接开启所有能力；但 lifecycle 本来用于退出/重载，不应附带开 secrets/eval 等权限。另一路 `config.write` 可以更新包括 `debug` 在内的设置，同样需要阻止它提升自身权限。

建议：

- 保留参数绑定与一次性 token，定位为“已批准操作的执行凭据”。
- `prepare` 返回 `operationId`、服务端生成的目标/变更摘要、状态与有效期；未批准时不返回可执行授权。
- 支持“批准一次”“在指定服务器/目录内限时批准一类动作”“拒绝”，保证常规自动化不必每条命令弹窗。
- 权限提升只允许独立的用户授权入口完成；MCP 可请求授权、查询结果、主动缩小权限，不能自行批准。
- 常规设置写入排除 debug 权限、监听范围、token/客户端授权等管理字段；它们进入专用策略管理入口。
- 执行时重新验证调用身份、目标、参数摘要、授权有效期及策略版本；取消授权后未执行的操作失效。

审批摘要不能只信任调用方传来的 summary，应由服务端根据实际参数产生，并单独展示调用方的说明。

证据：`internal/debugsrv/mcp.go:1320`、`:1364`；`internal/debugsrv/caps.go:574`；`internal/apphost/debug.go:1839`、`:554`。

### 3.2 P0：UI 操作与 eval 不是“只改内存、刷新即还原”

`ui.click` 会派发真实的 DOM 事件处理链，`ui.type` 会触发 input/change，且可提交表单。因此能触发保存设置、删服务器等业务操作。返回 `persisted:false` 只能表达工具自己没直接写库，不能表达最终没有持久化副作用。

任意 `eval_js` 在当前页面上下文中执行，还可触达页面已有的宿主绑定。只在 MCP 入口检查能力，无法约束这些旁路。

建议：

- 将 CSS/令牌实验、导航、任意 store patch、DOM 操作、任意 JS 分开描述；任意 UI 控制和 eval 明确归入完全信任的开发调试模式。
- 运维模式只开放语义化工具，不开放任意 store 修改与任意 JS；实验 patch 使用 store/字段白名单，避免修改凭据与权限状态。
- 业务变更统一进入携带调用身份的服务层，HTTP/MCP/自动化 UI 都不能跳过相应策略。
- 审批入口应独立于被自动化的 WebView，例如宿主原生确认窗口或隔离的可信授权通道；同一个可被 eval 操控的页面不能承担可信批准。
- UI 返回改为描述直接作用和已观测业务动作；无法追踪时返回副作用未知，避免承诺 `persisted:false`。

还要检查返回值旁路：`ui.store` 对非 ui store 已增加 secrets.read 校验，这是正确补救；但 `ui.storePatch` 的前端返回包含修改后的 state/valuesAfter，不能只保护只读入口。读取、写后回显、组件 props、控制台、错误、快照都需要统一的敏感字段策略。

证据：`frontend/src/debug/ui.ts:1013`、`:1268`、`:1323`；`internal/debugsrv/ui.go:847`、`:876`。

### 3.3 P0：文件白名单的保证范围需要收紧

当前写路径校验基于绝对路径字符串和路径段前缀，没有在写入前统一校验符号链接解析后的实际目标。白名单内的父目录链接可能把写入导向白名单外。

建议对现有目标及父目录做远端 canonical path 校验，明确是否允许跟随链接，覆盖 write/mkdir/rename/remove 和临时文件路径。新增目标应校验最近的已存在父目录；rename 要分别处理源、目标以及链接本身的语义。

限制：普通 SFTP 的路径检查与实际操作之间仍可能有竞态，不能宣称由此实现了完整文件系统沙箱。需要强隔离时使用受限远端账号、chroot 或受控代理。

同理，只要授予任意终端命令执行，调用方就可用 shell 写文件，SFTP 白名单只约束 SFTP 工具。任意本机 shell 还能接触同用户的发现文件与数据目录。因此“受限运维”模式不能同时授予任意本机 shell、任意 JS，再承诺这些限制不可绕过。

证据：`internal/debugsrv/sftp.go:266`、`:296`；`internal/apphost/debug.go:3312`、`:3562`。

### 3.4 P0：诊断导出与错误回显需要统一脱敏

诊断包直接把 `DebugInfoPath()` 指向的 `debug.json` 原样打包；该文件包含有效 token。日志脱敏并不能消除这个输出路径。诊断状态还可能包含终端可见文本，敏感数据读取开启时需要额外限制导出。

另有参数不一致错误拼接准备时与调用时的完整 JSON，confirm.prepare/commit 也返回 args。凭据相关输入不能通过错误、摘要或通用响应再次回显。

建议：所有诊断导出使用独立的安全投影，永不包含认证 token/私钥/密码；终端内容单独选择；确认工具只回敏感字段名称和内容摘要，不回明文。不能仅靠字段名正则保证任意终端文本无秘密。

证据：`internal/apphost/debug.go:1288`、`:1312`；`internal/debugsrv/confirm.go:300`；`internal/debugsrv/mcp.go:1320`、`:1430`。

### 3.5 P1：权限分类与实际影响不一致

| 当前情况 | 问题 | 建议 |
| --- | --- | --- |
| `terminal.input` 默认开，说明为“可逆/高频” | 输入可执行删除、提权和任意本机/远端命令，高频不等于可逆 | 首次接入默认观察模式；显式授权目标会话的执行能力 |
| 开关标签、断开/重连登记为 read | 新建连接或终止作业都会改变外部状态 | 增加 session.connect / session.disconnect，关闭前给出占用信息 |
| `servers.test` 归为 read | 实际会连接网络，登录测试还使用凭据 | 在策略上增加网络探测/连接权限与目标范围 |
| 读取权限不能关闭 | 终端、远端文件、截图可含业务秘密 | 拆出 app.read、terminal.read、fs.remote.read、ui.inspect 与各自对象范围 |
| sudo/凭据写入要求 secrets.read | 应用内部使用密码不需要向 AI 导出密码 | 分离 credentials.use、credentials.write、secrets.export |
| lifecycle 可作为扩权前置权限 | 退出应用与管理授权不属于同一权限 | 授权管理独立且由用户控制 |
| syncCwd 要 fs.remote.write 和写确认 | 仅切换面板目录，没有远端文件变更 | 归到 workspace/UI 导航，不要求文件写权限 |
| 取消传输要文件写权限和确认 | 只读下载也应能及时停止 | 以任务所有权和 transfer.cancel 控制，返回残留文件情况 |

不建议每个小工具增加一个设置开关。界面提供少数场景预设，底层用能力、对象范围、执行约束组合表达。

## 4. 尚未闭环、但很值得做的能力

### 4.1 P1：独立命令执行与任务生命周期

保留 terminal.run/expect 处理交互程序、shell 上下文和 TUI；新增后端独立 SSH exec 通道，避免与用户正在使用的 PTY 抢输入输出。

建议最小工具：

- `exec.start`：target/serverId、command 或明确的执行模式、cwd/env、超时、输出预算、授权引用、idempotencyKey，返回 jobId。
- `jobs.get` / `jobs.wait`：状态、退出码/信号、错误类别、时间、输出游标及截断信息。
- `jobs.output`：按 cursor 分页读取 stdout/stderr，不把 ANSI 屏幕缓冲当日志。
- `jobs.cancel`：区分停止等待、关闭 SSH channel、请求结束远端作业；无法保证远端进程已终止时明确返回取消未确认。

状态采用 queued/running/succeeded/failed/cancel_requested/cancelled/unknown；客户端超时不等于命令失败，连接丢失不等于远端进程已停止。持续任务需要外部进程监督或受控代理，不能声称普通 SSH channel 天然可断线续跑。

`terminal.run` 当前可等待 600 秒，而 stdio 代理单请求超时 120 秒；代理同步处理 stdin，一条长调用会阻塞后续取消/查询。这是执行模型需要优先改进的直接原因。

现有固定退出码标记也可能与历史/其他输出混淆；交互模式可升级为随机关联标记并说明 shell 支持范围。静默只代表暂时无输出，不能统一命名为执行完成。

任务元数据与有界输出按保留策略保存；提供查询幂等执行结果，禁止在结果不明时盲目重试 append、部署等副作用操作。幂等键需绑定身份、参数摘要和有效期，不承诺跨机器崩溃的任意副作用 exactly-once。

证据：`internal/debugsrv/sftp.go:552`、`:1948`；`cmd/ding-ssh-mcp/main.go:65`、`:539`。

### 4.2 P1：文件读改写、传输闭环

已有分片读取和目录分页，不需要重做。最有价值的补充是：

1. `sftp.write` 默认临时文件写入后替换，明确失败清理、权限保留及服务器不支持原子替换时的行为。仓库已有上传替换实现，可提取复用；append 单独定义，不能假设它有相同原子性。
2. 加入 expectedHash/expectedVersion，防止 AI 基于旧内容覆盖用户刚改的文件；校验与替换仍应说明跨进程竞态保证范围。
3. `sftp.patch`/编辑计划：读取 → 差异预览 → 有条件提交 → 回读验证；支持预览和可选备份，不强制所有大文件先下载全文。
4. `sftp.upload` / `sftp.download`、目录传输、校验和、进度与取消，与统一 jobs 关联；本地路径必须有独立授权根或使用用户选定的 artifactId，避免远端授权隐含本机文件读写权限。
5. 可选 `sftp.search`、权限修改、复制与磁盘空间查询，按真实使用频率逐项加入。

MCP 的当前覆盖写使用 O_TRUNC，已有普通上传的原子替换没有自动覆盖到这条路径。修改前先确认权限、ACL、链接以及跨文件系统 rename 的预期，避免只改名字就称为原子。

证据：`internal/apphost/debug.go:3562`；`internal/sshx/sftp_atomic.go`。

### 4.3 P1：连接、信任与认证闭环

补充 `sessions.get`、connect/disconnect/reconnect/wait 等语义化接口，明确 sessionId 与 tabId、serverId、连接代次的关系；保留 open_tab 等兼容别名。

连接结果应包含阶段、错误代码、可恢复动作和待处理 challenge。首次主机指纹、指纹变化、MFA/keyboard-interactive 请求应能被观察，敏感答案通过可信 UI 输入；MCP 不能自己批准首次信任或替换指纹。

已有 `hostTrust.list`，但没有完整 MCP challenge 工作流。应让调用方知道“为什么在等、需要用户做什么”，避免只得到超时或盲目关闭主机检查。

### 4.4 P2：结构化运维观测

复用已有 sysinfo/top/连接测试实现，提供主机 CPU、内存、磁盘、网络、进程和文件系统的结构化快照。返回采样时间、数据来源、权限不足、字段不可用原因。

优先做 `hosts.metrics`、`processes.list`、`tunnels.health`。再按 Linux 场景增加 services.status / services.logs / services.restart；服务重启必须绑定精确目标、授权和执行结果，不能伪装成读取工具。不同平台返回能力差异。

系统采集本身可能执行远端命令，应声明所需连接/执行条件和采样频率，不必每次采样都让用户确认。

### 4.5 P2：批量与变更计划

服务器过滤、按分组选择、连接测试聚合、有限并发的多机任务都有价值，但排在单机执行可靠之后。

批量修改先提供 dryRun/plan：冻结目标服务器与连接身份、列出变更、逐项审批或授予限定范围；执行返回逐目标结果与部分失败，支持停止后续调度。跨主机操作不承诺数据库事务式全局回滚，只为明确可逆的步骤提供补偿。

## 5. 协议与客户端工程需要补齐的部分

### 5.1 P1：MCP 契约一致性

- 明确支持的协议版本，保存初始化状态、协商版本和客户端能力；按协商版本输出字段。当前默认协商版本为 2025-03-26，同时提供 2025-06-18 的结构化输出，需用官方 SDK 客户端做兼容验证。
- 统一检查 JSON-RPC envelope、method/id、Content-Type、请求体超限、参数类型与范围；不能只把 schema 交给客户端自行遵守。当前存在小数截整数、错类型回默认值等宽松行为。
- 实现 `resources/templates/list`，声明 terminal/sftp 参数化资源。该方法缺失是互操作完善项，不应误写为整个 MCP 不可用。
- resources 声明 subscribe=false，却对 UI 变化主动发送 resources/updated；选择实现 subscribe/unsubscribe，或用明确声明和实现的通知机制发送，保持能力声明与行为一致。
- 工具/资源随会话变化时实现 listChanged 通知，或明确目录固定、运行时可用性另查。不要声明不变却依赖客户端自行猜测资源列表变化。
- `prompts/list` 当前为空且未宣告 prompts 能力。可保持不支持；若增加排障工作流提示，需配套 prompts/get，不必为凑完整度强行加入。
- 对核心工具提供完整 structuredContent/outputSchema；错误增加稳定 code、retryable、operationId、建议动作，保留中文说明。
- 添加 MCP tool annotations（readOnlyHint/destructiveHint/idempotentHint 等）帮助客户端展示；这些提示不能替代服务端授权。

可以评估引入维护中的官方 Go MCP SDK 承担传输与协议细节，现有业务 handler 和策略层继续复用。先做小范围兼容试验，再决定迁移，不为使用 SDK 而整体重写。

### 5.2 P1：事件、并发与资源管理

Hub 队列满会丢事件，Recent 按条数保存；当前 `droppedOutput` 标志针对单次捕获上限，不能当成 Hub 丢包总量检测。需要 seq/cursor、gap 标志和重新读取入口；高吞吐输出用可分页日志存储，SSE 只负责通知新增数据，避免终端流量淹没状态事件。

同一个 MCP session 的多个 GET 当前读取同一个 channel，可能分摊事件。应明确只允许一个活动推送连接，或为每个连接建立广播订阅；有界回放与 Last-Event-ID 可以后续实现，不必第一版就做完整事件存储。

MCP 会话增加数量上限、空闲 TTL、失联回收；任务、待审批操作、截图存档和输出都要有预算和清理策略。

终端互斥目前主要覆盖 run/expect/sudo，不能阻止 send_input 或用户键盘插入。交互任务应提供占用/干预状态；独立 exec 任务避免共享终端依赖。取消等待不能释放后立刻假定终端空闲。

### 5.3 P1/P2：身份、授权与部署边界

当前共享 Bearer token 与全局能力适合单个可信本地客户端；多客户端需要各自的 clientId/token/scopes/到期时间/撤销和审计归属。MCP sessionId 是传输会话，不是授权身份。

本地接口增加 Origin/Host 检查、请求大小/并发/连接数限制；不把日志采样误认为鉴权限流。逐步停止通过 query 传认证/确认 token，避免浏览器历史和代理记录携带凭据。

局域网模式目前使用明文 HTTP。建议第一阶段仍以 loopback 为主，远程通过 SSH 转发；若做正式远程接入，再规划 TLS、客户端认证、配对/撤销。只有需要通用远程 MCP 授权生态时再评估 OAuth，不把它作为本地版本前置条件。

审计保留现有 500 条内存环形用于 UI；对授权变更、文件改动、任务提交/取消增加可配置的持久化记录，包含 clientId、operationId、目标与结果。禁止把完整终端输入/输出当成天然安全的审计正文。

## 6. 建议的目标结构

```text
HTTP / MCP / 自动化前端入口
              ↓
统一调用身份与上下文（clientId / requestId / policyVersion）
              ↓
统一 ToolSpec + 入参校验 + 对象范围与能力校验
              ↓
变更计划 / 用户授权 / 幂等与任务状态
              ↓
应用业务服务 / SSH exec / SFTP / 工作区操作
              ↓
统一结果投影、敏感数据过滤、审计、事件游标
```

ToolSpec 集中维护名称、schema、handler、动态权限解析器、风险说明、支持平台、输出预算和确认要求。动态工具如 app.command、includeSecrets 或含凭据字段的 servers.update 必须按实际参数求权限，不能只看工具名。

能力组合建议：观察；限定目标的运维；完全信任的开发调试。普通用户看到这三类预设和目标范围，高级用户再展开细项。任意本机执行与任意 JS 属于高信任范围；若要求抵抗恶意客户端，需要操作系统/远端执行身份隔离，不能仅靠应用开关。

所有写操作尽可能走 inspect → plan → authorize → execute → verify，低风险且已获范围授权的操作可以直接执行。不要把创建分组、保存主题、删除目录全部描述为同一种“不可逆危险操作”。

## 7. 实施顺序与验收

### 阶段一：修权限与敏感数据边界

内容：真实审批/限时授权，禁止 MCP 自行扩权，分离权限管理设置；修 UI/eval 信任描述与旁路；credentials.use 与 secrets.export 分离；默认观察预设；诊断/确认/错误回显脱敏；SFTP 链接策略；统一 ToolSpec 和策略执行入口。

验收：

1. 只读客户端不能经 prepare/commit、settings、app.command、UI 间接获得未授权能力。
2. 仅授权服务器 A 时不能读写服务器 B，撤销后未执行操作失效。
3. 可使用保存的密码连接或 sudo，同时不能通过服务器查询、store patch、错误或导出取得明文密码。
4. 诊断包没有有效 token、密码或私钥；敏感终端内容默认不导出。
5. 白名单内链接指向外部时按既定策略拒绝；完整沙箱限制在文档中如实说明。
6. 对现有配置做显式迁移，不静默给旧客户端新增授权。

### 阶段二：补执行与文件可靠性

内容：exec.start + jobs 查询/输出/取消；stdio 支持并发请求和取消；事件游标与丢失检测；原子覆盖与条件写入；结构化错误；初始化/版本/schema 的兼容性修正；连接 challenge 可观测。

验收：

1. 慢输出、长时间无输出、大输出、远端退出、网络断开分别得到正确状态；超时不误报成功。
2. 调用响应丢失可用 jobId/幂等键查询，append/部署不被自动重复执行。
3. 用户终端输入不污染独立 exec 的输出；交互工具受干预时能说明状态。
4. 取消结果区分“已请求”和“确认终止”；客户端断开不丢失可查询结果。
5. 基于旧文件版本的写入被拒；中途写失败保留旧文件，临时文件按策略清理。
6. HTTP/stdio 客户端对初始化、工具/资源、错误、长调用和重连的行为一致。

### 阶段三：扩展业务闭环与体验

内容：上传下载、文件编辑计划、主机指标、隧道健康、有限并发多机任务；服务器搜索/分页；资源模板与订阅；按场景提供工具目录；按需补 macOS/Linux 截图。

当前截图底层只有 Windows 实现，HTTP 工具目录有 platformSupported 信息，但标准 MCP tools/list 缺乏同等明确的运行时可用性说明。先准确呈现不支持原因，再按平台实现捕获；不要把 macOS 上的像素验收当成已可用能力。

验收以实际任务衡量：连接到授权主机 → 观察 → 提交变更计划 → 获批 → 执行 → 回读验证 → 留下结果与审计；失败后能定位到具体阶段并继续处理。

## 8. 当前不建议优先投入

- 无限制的任意 JS、任意 store 写入继续扩展：会加重权限模型的不一致。
- 依靠字符串黑名单判断任意 shell 命令“安全”：无法覆盖 shell 展开、解释器与间接执行。
- 一次性追齐所有 MCP 可选特性：优先修当前已声明能力和真实客户端使用路径。
- 自动批准主机指纹变化、让 AI 读取主密码、自动跳过 MFA：不属于正常连接闭环所必需。
- 第一阶段就做多租户平台、全局事务式多机回滚或完全自动恢复：应先把单客户端、单主机任务做可靠。
