# ding-ssh UI 2.0 重构实施拆分

> 文档版本：v1.0（2026-11-02）
> 依据：[`../2.0设计规范.md`](../2.0设计规范.md) v1.0（Vercel Geist Developer Workbench 方向）
> 代码基线：`main@d0fe4c1`，前端 59 个文件 / 17,803 行（Vue + TS + CSS）
> 文档性质：**施工图**，不是设计稿。设计规范回答「做成什么样」，这里回答「先做什么、改哪个文件、怎么算做完、怎么退回去」。

---

## 1. 这套文档怎么用

1. 先读 [`00-现状盘点与约束.md`](./00-现状盘点与约束.md)：确认现有代码的耦合点、自动化契约和必须守住的东西。
2. 按 [`01`](./01-阶段0-基线与护栏.md) → [`02`](./02-阶段1-设计系统基座.md) → [`03`](./03-阶段2-应用外壳与终端工作区.md) → [`04`](./04-阶段3-业务页面与设置.md) → [`05`](./05-阶段4-交互自动化与交付.md) 顺序施工。
3. 每个阶段开工前读对应文件的「前置条件」，收工前用 [`08-验收矩阵.md`](./08-验收矩阵.md) 过门禁，并把结果写到 [`records/`](./records/README.md)。
4. 跨阶段共用的事项（设置迁移、旧变量/选择器映射、回滚）只看 [`06-兼容迁移与回滚.md`](./06-兼容迁移与回滚.md)。
5. 排期、依赖、提交切分看 [`07-任务总表与提交计划.md`](./07-任务总表与提交计划.md)。

> **执行原则：一次只推进一个工作包（WP），不跨阶段并行。** UI 重构的风险不在「改不动」，而在「改到一半时终端、SFTP、自动化和旧设置同时坏掉，无法判断是哪一刀切坏的」。

## 3. 阶段总览

| 阶段 | 目标 | 优先级 | 估时（人日） | 出口门禁（摘要） | 主要产物 |
|---|---|---|---|---|---|
| **P0 基线与护栏** | 在动手前把「什么不能坏」变成可测量、可回滚的东西 | P0 | 2–3 | 13 组基线快照齐全；选择器契约签字；5 份 ADR 定稿 | 快照集、契约表、ADR、验证命令 |
| **P1 设计系统基座** | 颜色/字体/圆角/间距/图标/基础组件全部收敛到 token 与 `components/ui` | P0 | 12–15 | 全局无硬编码色值；字体资源下降 ≥80%；终端渲染不受影响 | `theme/*.css`、`components/ui/*`、主题引擎 v2 |
| **P2 应用外壳与终端工作区** | 三栏布局、导航、顶栏、标签栏、终端区、右侧面板、分屏降级 | P0 | 14–17 | SSH/重连/多标签/本机 Shell/SFTP 联动/复制粘贴全部通过 | `layouts/*`、`views/TerminalWorkspace.vue`、App.vue ≤180 行 |
| **P3 业务页面与设置** | Overview/Servers/Tunnels/Transfers/Settings/Debug 全部按新规范重排 | P1 | 15–19 | 原 CRUD、持久化、设置保存/恢复、MCP 权限全部通过 | `views/*`、`components/server/*`、Settings 分区组件 |
| **P4 交互、自动化与交付** | 命令面板、快捷键、状态反馈、DOM 稳定标识、自动化回归、三平台与发布 | P1 | 8–10 | `ui.layout`/`ui.assert`/`ui.diff` 全部通过；三平台基础检查通过 | 命令面板、快捷键表、回归记录、发布说明 |

**合计：51–64 人日（1 名前端，不含设计返工与跨平台真机排队）。** 估时口径见 [07](./07-任务总表与提交计划.md)。

> **与设计规范 §17 的对应关系**：设计规范给出四个阶段（设计系统基础 / 主工作区 / 业务页面 / 交互与性能）。本拆分把「设计系统基础」之前再加一个 **P0 基线与护栏**（不改业务代码，只采集基线、冻结自动化契约、定 ADR），原来的四阶段依次对应 **P1–P4**。这样做的原因：本次改造最大的风险不是「做不出来」，而是「做完之后 AI 控制面定位不到元素、旧设置被迁移坏」，必须先有可回滚的基线。

## 4. 编号与状态约定

| 记号 | 含义 | 示例 |
|---|---|---|
| `P0`–`P4` | 阶段 | `P2` 应用外壳 |
| `WP2.3` | 阶段内工作包（Work Package） | 标签栏与终端头部 |
| `P2-15` | 可执行任务（**唯一的施工单元**） | 重做 TabBar |
| `D1`–`D10` | 设计规范与现状的差距/待决策项 | D1 默认主题迁移 |
| `R1`–`R12` | 风险登记项 | R1 自动化选择器失效 |
| `ADR-01`–`ADR-08` | 架构决策记录 | ADR-03 字体方案 |

任务状态只用四种：`待开始` / `进行中` / `待验收` / `已完成`。**「代码写完」不等于完成**，必须同时满足：

1. `npm run build`（含 `vue-tsc --noEmit`）通过；
2. 该任务在 [08](./08-验收矩阵.md) 中对应的验收项有记录；
3. 涉及界面的任务附带 `ui.snapshot` 前后对比或截图；
4. 涉及自动化契约的任务，`ui.layout` / `ui.assert` 已跑通；
5. 提交信息符合 [07 §7.2](./07-任务总表与提交计划.md) 的格式，且一个提交只做一件事。

## 5. 全局验证命令

```bash
# 1. 类型检查 + 生产构建（CI 同款）
cd frontend
npm run build

# 2. Go 侧回归（设置迁移、调试 API、MCP、命令规则都在这里）
cd ..
go test ./internal/...

# 3. 桌面壳构建（阶段门禁必跑，至少本机平台）
wails build

# 4. 开发态联调（调试模式需在设置里打开，或用 -debug 启动）
wails dev
```

UI 自动化验证（应用以调试模式运行后，通过 MCP / HTTP 调用）：

```text
ui.snapshot {name:"ui2-p2-before", selector:".app-shell"}   # 改前留档
ui.layout                                                   # 布局骨架 + 非预期重叠
ui.tokens {filter:"--"}                                     # 令牌落点
ui.assert {selector:"[data-ui=terminal]", visible:true}
ui.query  {selector:"[data-ui=terminal]"}                  # 看 total / rect / classes
ui.diff    {a:"ui2-p2-before", b:"ui2-p2-after"}
```

> 快照落在日志目录的 `logs/ui-snapshots/`，**不进 Git**。需要在团队间对比时，把 `ui2-*` 快照与验收记录一起归档到 [`records/`](./records/README.md) 对应阶段目录（图片可压缩后提交，或只提交 diff 摘要）。

## 6. 每个阶段的产物清单

每个阶段都必须产出以下 5 类东西，缺一不可：

| 产物 | 存放位置 | 说明 |
|---|---|---|
| ① 代码与提交序列 | Git 分支 | 按 [07 §7.2](./07-任务总表与提交计划.md) 切分，可单独 revert |
| ② 验收记录 | `docs/refactor-2.0/records/phase-N.md` | 用 [08 §7](./08-验收矩阵.md) 模板，逐项打勾并附快照名 |
| ③ 快照集 | `logs/ui-snapshots/ui2-pN-*` | 固定窗口 1440×900、uiScale 100、Dark；关键状态每组一张 |
| ④ 契约变更记录 | [06](./06-兼容迁移与回滚.md) 或阶段文档 | 新增/废弃的 CSS 变量、`data-ui`、设置字段、`ui.*` 选择器 |
| ⑤ 已知问题清单 | 验收记录末尾 | 明确「本阶段不修、留给哪个阶段」，不允许口头遗留 |

## 7. 与设计规范的偏差处理

设计规范中有若干处与当前代码、或与「不改变业务行为」原则存在张力（例如默认主题从青绿变蓝、右侧面板 340→300、状态栏 30→26、标签栏位置设置的去留）。这些**不在执行时临时拍脑袋**，统一在阶段 0 以 ADR 形式定稿，记录在 [06 §2](./06-兼容迁移与回滚.md)，并在 [00 §8](./00-现状盘点与约束.md) 的 D1–D10 表中回填决策。

已识别的 10 个待决策项（D1–D10）见 [00 §8](./00-现状盘点与约束.md)。**D1（默认主题迁移）、D6（字体方案）、D7（组件库落地方式）未定稿前，不得开始 P1。**

## 8. 一句话总结

> 先把「不能坏的东西」量化（P0），再把「视觉地基」换掉（P1），然后换「壳」（P2），再换「房间」（P3），最后把「操作方式」和「AI 控制面」补齐（P4）。每一刀都可单独回滚，任何一阶段结束后应用都必须是可发布状态。
