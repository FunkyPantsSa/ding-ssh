# 01 · 阶段 0：基线与护栏

> 优先级：P0　估时：2–3 人日　前置：无　出口：基线快照齐全 + 契约冻结 + 5 份 ADR 定稿
> 本阶段**不改任何业务代码**，只允许新增 `scripts/`、`docs/refactor-2.0/records/` 与最小验证脚本。

---

## 1. 阶段目标

把「不能坏的东西」从口头约定变成**可测量、可回滚**的资产：

1. 一套固定环境下的视觉基线快照，后续每一刀都能 `ui.diff` 出「到底变了哪里」。
2. 一份自动化选择器契约，明确哪些 DOM 钩子是 AI 控制面的依赖，改名前必须先加别名。
3. 5 份 ADR：4 份关键设计决策（字体、组件库、迁移、信息架构）与 1 份分支/提交策略，避免施工中反复推翻。
4. 一条可重复执行的验证命令，和一次真实的回滚演练。

**非目标**：不调整颜色、不换字体、不动布局、不拆 App.vue。

## 2. 工作包与任务

### WP0.1 基线快照（P0-01、P0-02）

#### P0-01 固定快照环境

| 项 | 固定值 | 说明 |
|---|---|---|
| 窗口尺寸 | 请求 1440×900 | 用 `ui.window {width:1440,height:900,restore:true}` 固定，并记录返回的 `inner`；macOS 标题栏下实测内容区为 1440×872，不能把外窗尺寸误写成内容区尺寸 |
| 界面缩放 | 100% | `settings.uiScale = 100` |
| 明暗 | Dark | **优先把操作系统切到深色**（`baseTone='auto'` 跟随）。不要用 `ui.storePatch` 改 `appearance.baseTone`：它会触发终端色板同步 watch，可能经 `settings.setTheme()` 落库，污染基线配置 |
| 服务器数据 | 3 台：`node-01`（在线）、`gpu-01`（离线）、`db-01`（未测试），1 个分组 | 用测试配置，避免用真实生产节点截图 |
| 会话 | 1 个已连接 SSH + 1 个本机终端 | 连接可用本地 `sshd` 或测试机 |
| 调试模式 | 开启、仅本机、能力位按默认 | 快照与自动化都需要 |
| 主题 | 当前默认（signal / auto→dark） | **记录实际 `appearance` 与 `data-tone`**，写入元信息 |

隔离运行要求：开发/自动化实例必须设置绝对路径环境变量
`DING_SSH_DEV_CONFIG_DIR=/tmp/...`。该目录统一承载数据库、旧 JSON、日志、快照、
`debug.json` 与测试密钥；测试实例不访问系统钥匙串。相对路径会被忽略，避免误把产物写进仓库。

执行命令模板：

```text
ui.window  {restore:true, width:1440, height:900}
ui.storePatch {name:"settings", patch:{uiScale:100}}
ui.snapshot {name:"ui2-p0-<state>", selector:".app-shell"}
ui.tokens   {filter:"--"}
```

#### P0-03 冻结自动化选择器契约

产物：`docs/refactor-2.0/records/phase-0.md` 中的「选择器契约表」（可直接复制 [00 §7.2](./00-现状盘点与约束.md) 的表并加一列「负责人签字」）。

规则：

1. **只增不删**：新结构必须同时保留旧 class/aria 选择器，至少到 P4-07。
2. **优先加 `data-ui`**：所有关键区域在 P2 开始时加 `data-ui="..."`，`ui.layout` 改为「`data-ui` 优先 + 旧选择器 fallback」。
3. **禁止依赖位置**：不允许用 `:nth-child`、`> div > div` 这类结构选择器做自动化断言。
4. **改名流程**：先在 `debug/ui.ts` 的 `LAYOUT_KEYS` 增加 fallback → 改 DOM → 跑 `ui.layout` → 再删除旧选择器。

### WP0.2 决策（P0-05 ~ P0-08）

#### P0-05 ADR-03：字体方案（D6）

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. Fontsource Geist | 安装 `@fontsource/geist-sans` / `@fontsource/geist-mono`，只引 3–4 个常用字重 | 与现有引入方式一致、许可证清晰（OFL）、体积可控 | 仍是多子集文件，需要裁剪 | **推荐** |
| B. 自托管 WOFF2 | 从官方仓库取 Geist 可变字体，转 WOFF2 子集 | 文件最少、可控 | 需要构建期子集化工具，维护成本高 | 备选 |
| C. 系统字体 | UI 用 system-ui，终端用系统 mono | 零体积 | 跨平台观感不一致，违背 Geist 方向 | 不采用 |

**验收预算**：字体文件 ≤32 个、字体总字节 ≤ 800 KB、`@font-face` ≤16 条、中文回退栈显式声明。若 A 方案实测超标，退回 B。

#### P0-06 ADR-04：组件库落地方式（D7）

| 方案 | 做法 | 风险 | 结论 |
|---|---|---|---|
| A. shadcn-vue 全量引入 | `npx shadcn-vue init` + 按需 add 18 个组件 | 依赖 reka-ui/cva/tailwind-merge；需 `@` 别名与 Tailwind v4 配置；网络 | **首选**，但先做最小 Demo（P1-10） |
| B. 自建同 API 组件 | 在 `components/ui` 手写 18 个组件，API 对齐 shadcn | 工作量大、可访问性要自己保证 | A 失败时启用 |
| C. 继续用全局 CSS 类 | 只换 token 不换组件层 | 无法解决弹层焦点/键盘/无障碍 | 不采用 |

**硬前提**：`vite.config.ts` + `tsconfig.json` 增加 `@` → `src` 别名；新增 `src/lib/utils.ts` 的 `cn()`。这两项与方案无关，P1-10 必做。

#### P0-07 ADR-05：设置迁移与降级（D1/D5/D10）

- 新增可选字段 `uiSchema`（见 [00 §4.3](./00-现状盘点与约束.md)）。
- 迁移规则：**仅当用户从未自定义**（`appearance` 等于旧默认、`theme` 等于旧默认、`fonts` 等于旧默认）才切到 Geist 默认；否则保留。
- 迁移前把 `appearance/theme/fonts/terminalColorMode` 备份到 localStorage。
- 迁移必须幂等；旧版本读新配置不崩；旧版本保存丢 `uiSchema` 后再次升级可重跑。
- 详细矩阵见 [06 §2](./06-兼容迁移与回滚.md)。

#### P0-08 ADR-07：信息架构（D5/D8）

必须一次性定稿的四件事：

| 问题 | 决策（建议） | 影响 |
|---|---|---|
| 标签栏位置 | 主工作区顶部固定；导航里的「Active Sessions」是**纵向会话列表**，不是第二套标签栏 | 删除 `TabBar side` 形态；`tabBarPlacement` 字段保留但 UI 移除 |
| 导航分组 | `WORKSPACE(Overview/Servers/Tunnels)` + `SESSIONS(Local Shell/Active Sessions)` + `TOOLS(Transfers/Command History)` + `SYSTEM(Settings/About)` | 新增 3 个 view；`navSectionOrder` 字段保留但 UI 移除 |
| 起始页 | 启动时若有恢复会话 → 工作区；否则 → Overview | 需新增 `overview` view 与 recent 数据 |
| 设置入口 | General 内的「高级」折叠 + 独立 Debug 页 | Debug 从设置页移出；section key `debug` 保留为跳转别名 |

> 若团队决定「起始页仍是工作区」，只改 P3-04 一个任务，不影响其他拆分；但必须在 P0 记录，避免 P3 反复。

### WP0.3 工程护栏（P0-09 ~ P0-11）

#### P0-09 分支与提交策略（ADR-01）

```text
main ────●────────────────●────────────●────────────●────▶
          \              /            /            /
           feat/ui2-p1 ──            /            /
                        feat/ui2-p2 ──           /
                                   feat/ui2-p3 ──
                                              feat/ui2-p4
```

- 每个阶段一个长分支，**阶段内按 WP 提交**；阶段门禁通过后才合入 `main`。
- 阶段分支每周从 `main` rebase 一次，冲突在当周解决（针对 `App.vue`/`SettingsPage.vue` 这类热点文件，优先先合入「拆分」提交，再合功能改动）。
- 不允许在阶段分支上顺手修业务 bug；bug 单独走 `fix/` 分支并先合 `main`。
- 阶段合并使用 `--no-ff`，保留阶段边界，便于整段 revert。

#### P0-10 验证脚本与 CI 对齐

新增 `scripts/verify-ui2.sh`（仅本地/CI 手动跑，不改 CI 默认行为）：

```bash
#!/usr/bin/env bash
set -euo pipefail
root="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"

echo "== frontend typecheck + build =="
(cd "$root/frontend" && npm run build)

echo "== go tests =="
(cd "$root" && go test ./...)

echo "== 字体/包体预算 =="
css=$(ls "$root"/frontend/dist/assets/*.css | head -1)
echo "css bytes: $(wc -c < "$css")"
echo "font files: $(ls "$root"/frontend/dist/assets/*.woff* 2>/dev/null | wc -l)"
echo "font-face: $(grep -o '@font-face' "$css" | wc -l)"
```

验收：

- 脚本在干净工作区可一次跑通；
- 输出的三项体积指标与 [00 §6](./00-现状盘点与约束.md) 的基线一致（作为 P1 对比基准）；
- CI 仍保持原默认门禁；本地 P0 脚本额外执行 `go test ./...`，覆盖根包、MCP CLI 与开发目录护栏。

#### P0-11 回滚演练

1. 在阶段分支造一个只改文案的提交，执行 `git revert <sha>`，确认无冲突、构建通过。
2. 备份 `settings.json`，手动改坏 `appearance.presetId`，启动应用确认 normalize 生效（回落默认）。
3. 恢复备份，确认服务器/凭证/隧道数据完好。
4. 把演练步骤与结果写入 `records/phase-0.md`。

## 5. 退出后进入阶段 1 的条件

1. 门禁全部打勾；
2. 阶段 0 记录合入 `main`；
3. 从 `main` 切出 `feat/ui2-p1`；
4. 在阶段 1 第一次改动前，再跑一次 `ui.snapshot {name:"ui2-p1-before", selector:".app-shell"}`，作为 P1 的「改前」基准。
